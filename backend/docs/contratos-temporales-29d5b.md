# 29D.5B — Contrato temporal conservador (pendiente 29D.5C)

## Regla de procedencia

La base **no** identifica por fila la política temporal usada al escribir. Las filas de 29D.3 y las creadas después de 29D.5A tienen los mismos campos. Por tanto un `datetime` leído del ORM/MySQL, incluso bajo `@@session.time_zone = '+00:00'`, **no acredita por sí mismo un instante UTC**. Tampoco lo acredita una cabecera HTTP antigua terminada en `GMT`, ni una comparación con el reloj actual. No se han convertido ni actualizado fechas históricas y no se han creado tablas, columnas ni migraciones.

`utils/clinical_dates.py` ofrece tres operaciones separadas: `utc_instant(datetime)` convierte aware a UTC ISO 8601 con `Z` (y acepta naive **solo** con `naive_origin='UTC'` probado por el llamador); `unverified_wall_time` conserva los componentes de una fecha naive persistida como ISO **sin zona**; `civil_date` conserva `YYYY-MM-DD` sin convertir el día. El código focalizado de lecturas clínicas evita que Flask asigne falsamente `GMT` a informes, revisiones, visitas, validaciones, listado y búsqueda de pacientes. El significado de los campos, controles de acceso, IDs, estados, número de revisión y contenido clínico no cambia. Los contratos nuevos sin zona indican **hora almacenada, procedencia no verificada**; no autorizan `new Date(value)` ni cálculo de edad o caducidad. No se aplica un proveedor JSON global. Fechas extraídas de nombres de exportación tampoco reciben `Z`.

La confirmación del retinógrafo mantiene su `fecha_expiracion` ISO con `Z`: su fecha fue generada y comparada como UTC naive en ese flujo; `utc_instant(..., naive_origin='UTC')` expresa esa garantía existente, sin tocar los 60 minutos, estado, fuente, copia ni comprobante. No se amplía esa afirmación a otros escritores externos.

## Presentación

`frontend/src/lib/clinicalDates.ts` acepta para conversión clínica solo ISO con `Z` u offset explícito. Formatea con `Intl.DateTimeFormat('es-PE', { timeZone: 'America/Lima' })`; no usa zona del navegador ni offset fijo. Un valor sin zona o el `GMT` HTTP legado muestra **«Fecha pendiente de conciliación»**, no una hora exacta. La utilidad distingue `YYYY-MM-DD` civil de un instante; edades y días civiles se calculan con el calendario Lima, no desplazando nacimientos con UTC. Las listas mantienen el orden recibido cuando falta un instante comparable; el historial sigue ordenado por `numero_version`. Una comparación de visitas sin procedencia temporal ya no se etiqueta falsamente como «anterior/posterior». La selección automática de visitas *recientes* no utiliza edades temporales no acreditadas: puede quedar vacía hasta 29D.5C; no altera reglas de inferencia ni permite un bypass. Las respuestas tardías, autorización y modo solo lectura se conservan.

## PDF

La generación actual utiliza un reloj aware para el momento **de generación**, presentado en `APP_TIMEZONE` (`America/Lima` por defecto). Una visita/validación histórica naive de procedencia desconocida no se convierte: se imprime «Fecha pendiente de conciliación» y el archivo usa `fecha-no-conciliada`, no un día clínico inventado. Nacimiento (`DATE`) mantiene su día. Una fecha UTC **aware y acreditada** se convierte a Lima, incluyendo cruces de medianoche. Si Windows carece de datos IANA, el fallback ya existente `-05:00` solo se ensayó con fechas contemporáneas sintéticas; no demuestra el comportamiento histórico de verano ni debe usarse para reconciliar historiales. La plantilla, inferencia, imágenes y autorización no se modificaron.

## Dependencia y transición obligatoria

Esto **no** normaliza automáticamente la lectura de filas nuevas persistidas: sin procedencia por fila, la representación segura continúa siendo «no verificada». 29D.5C debe acordar un marcador fiable o una conciliación autorizada por origen y período comprobables, conservar originales y tratar los casos indeterminables como tales; cualquier DDL requeriría aprobación y respaldo verificable posterior a 29D.3. Solo después se puede habilitar `Z` para las filas acreditadas y restaurar búsqueda por ventana temporal, comparación cronológica y nombre de PDF con fecha clínica. Verificar también otros consumidores API que aún esperen el anterior HTTP `GMT`; no desplegar 29D.5A/B aisladamente en la base habitual. Las banderas de edición, anulación e historial siguen apagadas fuera de pruebas MySQL desechables. No se hizo E2E de navegador ni se usaron imágenes clínicas reales.
